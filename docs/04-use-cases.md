# ユースケース一覧（要件定義 v2）

> **このドキュメントの目的**
> Phase 1-A で確立したドメインモデルに沿った、ユーザー視点でのユースケース（機能仕様）を定義する。MVP（Phase 1）のスコープのみを記載。
>
> **DDD的位置づけ**
> ユースケース = アプリケーション層が提供する操作。後の実装で `application/` レイヤーの「アプリケーションサービス」になる単位。各ユースケースは「どの集約をどう操作するか」が中核。

---

## 0. アクター（登場人物）

| アクター | 説明 | 権限 |
|---|---|---|
| 管理者 | チーム運営者（NGOhiroshiさん）。メンバー登録、機密情報閲覧などができる | 全機能 |
| 一般メンバー | チーム所属の選手 | 試合記録の閲覧、自分の成績閲覧、スコア入力（管理者と同等で良いか後で検討） |
| 未認証ユーザー | ログイン前 | ログイン画面のみ |

> 💡 MVP では管理者と一般メンバーの権限差分は最小に。スコア入力は両者が可能とする。**機密情報管理は Phase 2** なので権限差分は実質ほぼなし。

## 1. 認証

### UC-AUTH-1: ログイン
- **アクター**: 未認証ユーザー
- **前提**: Supabase Auth にユーザーが登録済み
- **メインフロー**:
  1. ログイン画面で Email を入力
  2. Magic Link がメールに届く
  3. リンクをクリックしてセッション確立
  4. メイン画面（試合一覧）に遷移
- **代替フロー**: Google OAuth でのログイン（任意）
- **事後条件**: ユーザーは自身のチームのデータにアクセス可能

### UC-AUTH-2: ログアウト
- **アクター**: 認証済みユーザー
- **メインフロー**: 設定メニューから「ログアウト」をタップ → セッション破棄 → ログイン画面へ

## 2. チーム管理コンテキスト

### UC-TEAM-1: メンバー登録
- **アクター**: 管理者
- **前提**: ログイン済み
- **メインフロー**:
  1. メンバー一覧画面から「+ 新規メンバー」をタップ
  2. 選手名、顔写真（任意）、権限（admin/regular）を入力
  3. 保存
- **影響を受ける集約**: `Team`
- **事後条件**: メンバーがチームに追加される

### UC-TEAM-2: メンバー編集
- **アクター**: 管理者
- **メインフロー**: メンバー一覧 → 該当メンバーをタップ → 情報を編集 → 保存

### UC-TEAM-3: メンバー削除
- **アクター**: 管理者
- **メインフロー**: メンバー詳細から「削除」 → 確認ダイアログ → 削除
- **注意**: 過去の試合データに紐づくメンバーIDは保持される（参照整合性は緩く保つ）

### UC-TEAM-4: 助っ人選手の臨時登録
- **アクター**: 管理者または一般メンバー
- **メインフロー**:
  1. 試合の打順登録画面で「助っ人を追加」をタップ
  2. 助っ人の名前のみを入力
  3. 打順に組み込む
- **影響を受ける集約**: `Team`（助っ人プールに追加）+ `Game`（打順に登録）

### UC-TEAM-5: メンバー一覧の閲覧
- **アクター**: 全ユーザー
- **メインフロー**: メニュー → 「メンバー」 → 一覧表示（写真付き）

## 3. 試合記録コンテキスト ★ 中核

### UC-GAME-1: 試合の作成
- **アクター**: 管理者または一般メンバー
- **メインフロー**:
  1. 試合一覧画面で「+ 新規試合」をタップ
  2. 試合日、対戦相手名を入力
  3. 保存（この時点でイニングスコア・打順・打席結果は空）
- **影響を受ける集約**: `Game`（新規作成）
- **事後条件**: 空の試合データが作られ、試合詳細画面に遷移

### UC-GAME-2: 打順登録
- **アクター**: 管理者または一般メンバー
- **前提**: 試合が作成済み
- **メインフロー**:
  1. 試合詳細画面で「打順を登録」をタップ
  2. メンバー一覧から選手を選択し、1番から順に並べる（**参加人数分、上限なし**。例: 12人参加なら12番まで）
  3. （任意）助っ人を追加で登録する
  4. （任意）各選手に守備位置を設定する
  5. 保存
- **不変条件**: 打順番号は重複不可、1人以上、上限なし
- **影響を受ける集約**: `Game.battingOrder`
- **代替フロー**: 既に登録済みの打順を編集することも可能

### UC-GAME-3: 打席結果の入力（新規作成 / 編集）
- **アクター**: 管理者または一般メンバー
- **前提**: 打順が登録済み
- **メインフロー**:
  1. 試合詳細画面で打順をタップ → 当該選手の「+ 打席を追加」（既存の打席をタップした場合は編集モード）
  2. 上位カテゴリを選択（安打 / 出塁 / 凡退 / 犠打犠飛 / 失策のみ）
  3. 下位カテゴリを選択（例: 安打 → 単打/二塁打/三塁打/本塁打）
  4. （安打/失策のみの場合）打球方向を **4分類（左 / 中 / 右 / 内野）** から選択
  5. （凡退/犠打犠飛/失策のみの場合）守備位置を入力（任意）
  6. （安打の場合）「失策あり」フラグを必要に応じて設定
  7. （必要に応じて）打点を入力
  8. **「この後ホームに帰った（得点した）」フラグ** を必要に応じてチェック（後から戻って編集可能）
  9. 保存
- **重要なUX要件**: 得点はホームインのタイミングが打席より後になる。**過去の打席を後から再度開いて `runScored` チェックを入れ直せる**こと必須。
- **不変条件**: カテゴリの排他、`hadError` は `hit` カテゴリでのみ意味を持つ
- **影響を受ける集約**: `Game.plateAppearances`

### UC-GAME-4: イニングスコア入力
- **アクター**: 管理者または一般メンバー
- **前提**: 試合が作成済み
- **メインフロー**:
  1. 試合詳細画面の「スコアボード」エリアで該当イニングをタップ
  2. 自チーム得点・相手得点を入力
  3. 保存
- **不変条件**: イニング番号の重複禁止、得点は0以上
- **影響を受ける集約**: `Game.inningScores`
- **事後条件**: 試合詳細の最終スコアが自動更新される

### UC-GAME-5: 投手交代・イニング単位の投手成績入力
- **アクター**: 管理者または一般メンバー
- **前提**: 試合が作成済み
- **メインフロー（投手の登板開始時）**:
  1. 試合詳細画面で「投手交代」をタップ
  2. 投手をメンバー一覧から選択、登板開始イニングを設定
  3. 保存
- **メインフロー（イニング終了時）**:
  1. 試合詳細の投手成績エリアで「+ イニング記録を追加」
  2. イニング番号、被安打・失点・自責点・四死球・奪三振・このイニングで取ったアウト数 を入力
  3. 保存
- **不変条件**:
  - `earnedRuns ≤ runsAllowed`
  - `outsRecorded` は 0〜3
  - 投手交代の時系列が逆転しない
- **影響を受ける集約**: `Game.pitchingAppearances`（および子の `inningRecords`）

### UC-GAME-6: 試合詳細の閲覧
- **アクター**: 全ユーザー
- **メインフロー**: 試合一覧 → 試合をタップ → 試合詳細画面
  - 表示内容: イニングスコア（スコアボード形式）、最終スコア、打順と打席結果一覧、投手成績

### UC-GAME-7: 試合一覧の閲覧
- **アクター**: 全ユーザー
- **メインフロー**: メニュー → 「試合」 → 試合一覧（試合日の降順）

### UC-GAME-8: 試合の削除
- **アクター**: 管理者
- **メインフロー**: 試合詳細 → 「削除」 → 確認ダイアログ → 削除
- **影響を受ける集約**: `Game`（カスケード削除で打順・打席・投手記録も削除）

## 4. 成績集計コンテキスト

### UC-STAT-1: 個人打撃成績の閲覧
- **アクター**: 全ユーザー
- **メインフロー**:
  1. メンバー一覧 → メンバーをタップ → メンバー詳細
  2. 「打撃成績」タブを開く
  3. 年度切替（2026年 / 通算）
- **表示項目**: 打席数・打数・安打数・本塁打数・打率・打点・得点
- **算出元**: `plateAppearances` テーブルからリアルタイム集計（クエリベース）

### UC-STAT-2: 個人投手成績の閲覧
- **アクター**: 全ユーザー
- **メインフロー**:
  1. メンバー詳細 → 「投手成績」タブを開く
  2. 年度切替（2026年 / 通算）
- **表示項目**: 投球回・防御率・奪三振・与四死球・被安打・失点・自責点
- **算出元**: `inning_pitched_records` から集計

### UC-STAT-3: チーム成績一覧の閲覧
- **アクター**: 全ユーザー
- **メインフロー**: 「成績」メニュー → チームメンバー全員の打撃成績/投手成績を一覧表示
- **ソート**: 打率順、本塁打数順、防御率順など

### UC-STAT-4: CSV エクスポート
- **アクター**: 管理者
- **メインフロー**:
  1. 成績一覧画面で「エクスポート」をタップ
  2. 年度・データ種別（打撃/投手）を選択
  3. CSV ダウンロード
- **目的**: バックアップ、他サービスへの移行可能性確保

## 5. ユースケース → 集約マッピング

| ユースケース | 主に操作する集約 | 操作タイプ |
|---|---|---|
| UC-TEAM-1〜5 | `Team` | コマンド（書き込み） |
| UC-GAME-1〜5, 8 | `Game` | コマンド |
| UC-GAME-6, 7 | `Game` | クエリ（読み取り） |
| UC-STAT-1〜4 | （読み取りモデル） | クエリ |

> 🎯 **DDD学習ポイント**:
> ユースケースを実装する層を **アプリケーション層（application service）** と呼ぶ。
> 例: `CreateGameUseCase` クラスが `UC-GAME-1` を実装し、`GameRepository.save()` を呼ぶ。
> アプリケーション層自身に**ドメインルールは書かない**。集約とドメインサービスにルールを委ねる「薄い指揮者」の役割。

## 6. MVP の機能優先度（実装順の参考）

| Pri | ユースケース | 理由 |
|---|---|---|
| P0 | UC-AUTH-1, UC-TEAM-1, UC-TEAM-5, UC-GAME-1 | 何もできない状態から最小限の操作 |
| P0 | UC-GAME-2, UC-GAME-3 | 草野球アプリの核心 |
| P0 | UC-GAME-6, UC-STAT-1 | データを見られないと使う意味がない |
| P1 | UC-GAME-4, UC-GAME-5, UC-STAT-2 | スコアボード・投手成績 |
| P1 | UC-TEAM-4 | 助っ人対応（試合で必要） |
| P2 | UC-TEAM-2, UC-TEAM-3, UC-GAME-8 | 編集・削除（運用しながら必要に応じて） |
| P2 | UC-STAT-3, UC-STAT-4 | チーム一覧・エクスポート |

> Phase 1-D の垂直スライス（実装フェーズ）では、上の優先度に従って5本のスライスを構成する。

## 7. 非機能要件（再確認）

| 項目 | 要件 | 検証方法 |
|---|---|---|
| モバイルファースト | スマホ画面（375〜414px幅）で快適に操作可能 | 実機テスト |
| レスポンス | 通常操作の体感1秒以内 | 試合中の入力で実証 |
| データ永続性 | DB バックアップを CSV エクスポートで取得可能 | UC-STAT-4 |
| 認証 | Supabase Auth による Magic Link / Google OAuth | UC-AUTH-1 |
| 権限分離 | 管理者と一般メンバーで操作可能範囲が異なる（MVPは最小差分） | UC定義参照 |
