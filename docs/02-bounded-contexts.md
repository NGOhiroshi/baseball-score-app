# 境界づけられたコンテキスト（Bounded Contexts）

> **このドキュメントの目的**
> このアプリのドメインを、責務ごとに分離した「コンテキスト」として整理する。コードの大きな構造（モジュール分割）は、ここで定義した境界に従う。
>
> **DDD的位置づけ**
> 大規模なドメインを1つの巨大モデルで表現すると破綻する。**「関心ごとに分けて、それぞれの中で完結したモデルを持つ」**のが境界づけられたコンテキストの本質。同じ単語でもコンテキストが違えば意味が違ってよい（例: `Player`は「試合記録」では選手、「成績集計」では集計対象）。

## 2. 各コンテキストの定義

### 2.1 チーム管理コンテキスト（Team Management Context）

**責務**: チームとそのメンバーのライフサイクル管理。認証・権限制御もここに含む。

**主な関心ごと**:
- メンバーの登録・更新・削除
- 助っ人選手の一時登録
- 管理者権限の付与
- ユーザー認証（Supabase Auth との連携）

**この中のモデル**:
- `Team`（集約ルート）
- `Member`（チームに所属する選手）
- `GuestPlayer`（試合ごとの臨時選手）

**他コンテキストへの提供**:
- 「選手ID → 選手名・写真」の参照（試合記録・成績集計から問い合わせ）

**境界の理由**:
- 選手の登録更新と、試合の進行は**ライフサイクルが完全に別**。
- 試合中にメンバー編集をすることはほぼなく、別の操作タイミング。
- メンバー削除しても過去の試合記録は残るべき（参照整合性は緩く保つ）。

---

### 2.2 試合記録コンテキスト（Game Recording Context）

**責務**: 1試合の進行を記録する。打順・打席結果・投手交代を扱う。**草野球ドメインの中核**。

**主な関心ごと**:
- 試合の作成（対戦相手・日付・最終スコア）
- 打順登録（選手の並び）
- 打席結果の入力（安打/出塁/凡退/失策）
- 投手の登板区間の記録（投手交代）

**この中のモデル**:
- `Game`（集約ルート）
- `BattingOrderEntry`（打順1〜9番）
- `PlateAppearance`（1打席分の記録）
- `PitchingAppearance`（1人の投手の登板区間）

**他コンテキストからの参照**:
- チーム管理から「選手ID」を取得して打順に紐づける（選手の実体は持たない、IDのみ）

**他コンテキストへの提供**:
- 試合データを成績集計が読み取る（イベントまたは直接参照）

**境界の理由**:
- **試合進行中のデータ整合性**を、他のコンテキストの都合で壊したくない。
- 打順・打席結果・投手交代は1試合の中でしか意味を持たない → 1試合を集約として扱える。
- ドメインルール（安打/出塁/凡退の排他、安打+失策の重複許可）はここに閉じ込める。

---

### 2.3 成績集計コンテキスト（Statistics Context）

**責務**: 試合データから個人成績・チーム成績を計算して提供する。**読み取り中心**。

**主な関心ごと**:
- 選手別の打撃成績（打率・打点・本塁打など）
- 選手別の投手成績（防御率・奪三振など）
- 年度別 / 通算の集計
- CSV エクスポート

**この中のモデル**:
- `PlayerBattingStats`（読み取り専用の集計データ）
- `PlayerPitchingStats`（読み取り専用の集計データ）

**他コンテキストからの参照**:
- 試合記録コンテキストの打席結果・登板情報を読み取る
- チーム管理コンテキストの選手情報を読み取る（表示用に名前・写真を引く）

**境界の理由**:
- **書き込みと読み取りでモデルが違う**（CQRS 的発想）。
- 試合記録モデルをそのまま画面に出すと使いづらい → 集計モデルを別途持つ。
- 集計ロジック（打率の計算式など）が試合記録の集約を肥大化させないよう分離する。

## 3. コンテキスト間の関係（パターン分類）

DDD ではコンテキスト間の関係性を呼び方で区別する。MVP で出てくる主要パターン：

### 3.1 チーム管理 → 試合記録：**「公開ホストサービス」（Open Host Service）**
- チーム管理側がメンバー情報のAPI（取得用）を提供。
- 試合記録側は「選手ID」だけを保持し、表示時にチーム管理に問い合わせる。
- 利点: メンバー情報の変更が試合記録に影響しない。

### 3.2 試合記録 → 成績集計：**「公開イベント」または「直接参照」**
- MVPでは**シンプルに直接参照（成績集計が試合記録のテーブルをSELECTで読む）**を採用。
- イベント駆動（試合記録更新→成績集計再計算をイベントで通知）は将来検討。

### 3.3 全コンテキスト ← 共有カーネル：**ユビキタス言語辞書**
- 用語定義は全コンテキストで共有する（このリポジトリの `docs/01-ubiquitous-language.md`）。

## 4. ディレクトリ構造への反映（先取り）

Phase 1-C の技術基盤セットアップで、コンテキストごとにディレクトリを切る。**この境界線がコードの構造**になる：

```
src/
├── contexts/
│   ├── team-management/      ← チーム管理コンテキスト
│   │   ├── domain/
│   │   ├── application/
│   │   └── infrastructure/
│   ├── game-recording/       ← 試合記録コンテキスト
│   │   ├── domain/
│   │   ├── application/
│   │   └── infrastructure/
│   └── statistics/           ← 成績集計コンテキスト
│       ├── domain/
│       ├── application/
│       └── infrastructure/
├── shared/                   ← 共有カーネル（ID型・共通エラー等）
└── app/                      ← Next.js のルーティング（薄い層）
```

> 💡 **DDD学習ポイント**: コンテキスト境界を**フォルダ構造に反映**することで、「依存関係の方向」を可視化できる。たとえば `game-recording` から `team-management` の `domain/` 内部を直接 import するのは禁止 → 公開された型・APIを経由してアクセスする、という規律になる。

## 5. Phase 2 で追加予定のコンテキスト（参考）

### マルチテナント（Tenancy Context）
- すべてのコンテキストに「テナントID」を横串で通す
- Supabase の RLS（Row Level Security）でテナント分離

### 機密情報管理（TeamSecret Context）
- 管理者専用の情報（備品のID/PW等）
- 暗号化保存と権限制御が中心の関心ごと
- 試合記録・成績集計とは完全に独立

### 過去データインポート（Historical Import Context）
- CSV または手動入力で過去成績を取り込む
- 集計コンテキストに合流するが、「現役の試合記録」とは別ライフサイクル
