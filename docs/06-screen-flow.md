# 画面遷移ラフ（モバイルファースト）

> **このドキュメントの目的**
> スマホで試合中に使うことを前提に、主要な画面と遷移を整理する。Phase 1-C 以降の Next.js ルーティング（`app/` ディレクトリ）の構成元になる。
>
> **DDD的位置づけ**
> 画面 = プレゼンテーション層。**画面はユースケースを呼び出す薄い層**で、ドメインロジックは持たない。「この画面でどのユースケースを起動するか」をマッピングする。

---

## 0. 設計方針

1. **スマホ縦画面前提**（375〜414px幅）
2. **試合中の入力**を最優先：タップ数最小、誤タップしにくいUI
3. **下部ナビゲーション**で主要セクション切り替え（ホーム / 試合 / メンバー / 成績）
4. **モーダルやBottom Sheet** を活用して画面遷移を抑える
5. PCからは閲覧主体（成績一覧などはPC幅でも見やすく）

### 2.4 打順登録 `/games/[gameId]/batting-order`

```
┌──────────────────────────────┐
│ ← 打順登録                    │
├──────────────────────────────┤
│ 1番 [選手を選択 ▼] [守備▼]    │
│ 2番 [田中 ▼]      [SS ▼]    │
│ 3番 [佐藤 ▼]      [- ▼]     │
│ 4番 [鈴木 ▼]      [- ▼]     │
│ ...                         │
│ 12番 [助っ人A ▼]   [- ▼]    │ ← 参加人数分追加可
│ [+ 打順を追加]                │
│ [+ 助っ人を追加]              │
│                              │
│ [キャンセル]  [保存]           │
└──────────────────────────────┘
```

> 💡 **打順の上限なし**: 9人を超えても「+ 打順を追加」で何人でも追加可能。草野球では参加者全員が打席に立てるよう、12人なら12番まで登録できる。
> 💡 **守備位置は任意**: ハイフン「-」で未指定を表現。試合中に頻繁にポジションが変わる草野球の実態に合わせる。

**対応UC**: UC-GAME-2（打順登録）、UC-TEAM-4（助っ人臨時登録）

        │ 「安打」を選択
        ▼
┌────────────────────────────┐
│ 田中 - 安打を選択           │
├────────────────────────────┤
│  [単打] [二塁打] [三塁打]  │
│         [本塁打]            │
│                            │
│ 打球方向（4分類）:           │
│   [ 左 ] [ 中 ] [ 右 ]      │
│         [ 内野 ]            │
│                            │
│ ☐ 失策あり (1H1E)          │
│                            │
│ 打点: [0] (+)              │

## 3. ルーティング設計（Next.js App Router 想定）

```
src/app/
├─ layout.tsx               ← 共通レイアウト（下部ナビ含む）
├─ page.tsx                 ← ホーム / 試合一覧
├─ login/
│   └─ page.tsx
├─ games/
│   ├─ new/
│   │   └─ page.tsx         ← 新規試合作成
│   └─ [gameId]/
│       ├─ page.tsx         ← 試合詳細（ハブ）
│       └─ batting-order/
│           └─ page.tsx     ← 打順登録
├─ members/
│   ├─ page.tsx             ← メンバー一覧
│   ├─ new/
│   │   └─ page.tsx
│   └─ [memberId]/
│       └─ page.tsx         ← メンバー詳細
└─ stats/
    └─ page.tsx             ← チーム成績ランキング
```

> 💡 打席結果入力、イニングスコア編集、投手記録は**モーダル**として実装する想定（ルートを切らない）。試合詳細画面の状態として開閉する。

## 4. プレゼンテーション層 ↔ アプリケーション層の境界（DDD観点）

各画面のボタンは、アプリケーション層の **ユースケースクラス**を呼び出すだけ：

| 画面のアクション | 呼び出すユースケース |
|---|---|
| 「+ 新規試合」保存 | `CreateGameUseCase.execute({ gameDate, opponentName })` |
| 打順登録「保存」 | `RegisterBattingOrderUseCase.execute({ gameId, entries })` |
| 打席結果モーダル「保存」 | `RecordPlateAppearanceUseCase.execute({ gameId, playerId, result })` |
| イニングスコア「保存」 | `UpdateInningScoreUseCase.execute({ gameId, inningNumber, ourScore, opponentScore })` |
| 投手記録「保存」 | `RecordInningPitchedUseCase.execute({ pitchingAppearanceId, ... })` |
| 打撃成績ページ表示 | `GetPlayerBattingStatsQuery.execute({ memberId, year })` |

> 🎯 **DDD学習ポイント**:
> 画面コンポーネントには **ドメインルール（打率計算など）が漏れてはいけない**。すべてユースケース経由で操作する。
> ボタン onClick → ユースケース呼び出し → 結果を state に反映、というシンプルな流れ。
> このルールを守ると、画面の見た目を変えてもドメインに影響が出ない（保守性が高い）。
